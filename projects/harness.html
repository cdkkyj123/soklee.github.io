Harness V4.3 Private System

개인 설계 · AI 엔지니어링 · 2026

Claude Code 기반 20개 전담 에이전트 개발 자동화 오케스트레이션 시스템

Overview

소프트웨어 개발의 전 단계(기획→설계→구현→검증→배포)를 전담 에이전트가 릴레이 방식으로 처리하는 개인 AI 엔지니어링 시스템입니다. 단순 AI 자동완성이 아닌, 각 Phase의 책임과 경계를 명확히 나눈 오케스트레이션 파이프라인으로 설계했습니다. 이 포트폴리오 사이트 자체가 Harness V4.3을 통해 Phase 0~5 전체 파이프라인으로 제작된 산출물입니다.

Phase 파이프라인

Phase 0~2: 기획·설계 단계

CEO → 전략 방향·프로젝트 경중 결정. PM + RESEARCH (병렬) → PRD 작성·기존 패턴 조사. ARCHITECT → Blueprint 설계. BLUEPRINT CRITIC → 핑퐁 리뷰(최대 2라운드).

DESIGN GATE: 사용자 승인 전 구현 진행 불가. 설계 완성도 강제.

Phase 2.5~3b: 구현 단계

PLANNER + DOCS (병렬) → 브랜치 생성·초기 ADR 문서화. TEST → 기존 패턴 파악 후 RED 테스트 선행. BACKEND + FRONTEND + DB → 병렬 구현. 완료 즉시 인프라 체크 + 테스트 GREEN 검증.

Phase 4~5: 검증·배포 단계

REVIEW + SECURITY + UIUX → 코드 품질·보안·접근성 검증. DOCS → 보안·테스트·성능 문서화. RELEASE → DEVOPS + DOCS → PR 생성·배포·최종 문서화.

에이전트 구성 (20개)

CEO PM RESEARCH ARCHITECT BLUEPRINT CRITIC PLANNER TEST BACKEND FRONTEND DB UIUX REVIEW SECURITY DOCS DEVOPS RELEASE DEBUG CONSULT CONDUCTOR META

각 에이전트는 전담 책임 범위와 사용 모델(Opus/Sonnet/Haiku)이 고정됩니다. 오케스트레이터(본인)는 설계·조율만 담당하며 직접 구현하지 않습니다.

7 Non-Negotiables

1. QUICK Check

수정 파일 ≤3·새 DB 없음·외부 의존성 없음·비즈니스 로직 변경 없음·동시성·트랜잭션 경계 변경 없음·"빠르게/간단히" 키워드 — 6가지 모두 충족 시만 QUICK 에이전트 단독 처리. 하나라도 미충족 시 전체 파이프라인.

2. Design Gate

ARCHITECT Blueprint 완료 → 사용자 승인 대기. 승인 전 Phase 2.5 진행 절대 불가. 설계 완성도를 구현 전에 강제로 검증.

3. Orchestrator Never Implements

오케스트레이터(메인 Claude)는 설계·조율만 담당. 모든 구현(Edit/Write)은 전담 에이전트 경유 필수. Edit/Write 도구 호출 직전 "내가 직접 구현하는 것인가?" 자문 — YES면 즉시 중단.

4~7. DOCS 필수 · 테스트 자동 실행 · Checkpoint 우선 · Edit/Write Guard

Phase 2.5·4.5·5에서 DOCS 에이전트 호출 필수(미호출 = Phase 미완료). Phase 3b 완료 즉시 테스트 GREEN 확인 후 Phase 4 진입. Phase 완료 후 checkpoint.md 저장 전 다음 Phase 진행 불가.

설계 결정

왜 Phase 기반 파이프라인인가

AI에게 "전부 해줘"를 주면 설계 없이 구현으로 달려가거나, 검증을 생략하는 경향이 있습니다. Phase 경계를 명확히 나누고 Phase 간 Gate(DESIGN GATE, Checkpoint)를 두면 AI의 성급함을 구조적으로 억제할 수 있습니다. 체크포인트는 세션 한도 초과 시 재개점으로도 기능합니다.

왜 에이전트 전문화인가

단일 범용 AI에게 모든 역할을 맡기면 맥락이 오염되어 점점 일관성이 떨어집니다. 역할별 에이전트를 분리하면 각 에이전트가 자신의 책임 범위에만 집중해 품질이 올라갑니다. SECURITY 에이전트는 "보안 취약점"만 보고, UIUX 에이전트는 "접근성·사용성"만 봅니다.

왜 "Orchestrator Never Implements" 원칙인가

오케스트레이터가 직접 코드를 작성하면 설계·구현·검증이 한 흐름에서 섞여 편향이 발생합니다. 설계자와 구현자를 분리해야 "내가 설계한 것을 내가 검증"하는 확증 편향을 차단할 수 있습니다. 이것은 소프트웨어 팀에서 설계자와 개발자를 분리하는 이유와 같은 원리입니다.
