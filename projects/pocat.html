Overview

포켓몬 카드 수집가들을 위한 C2C 경매 거래 플랫폼입니다. 판매자가 카드를 배송하면 관리자 검수 후 경매가 등록되고, 구매자는 입찰 또는 즉시 구매로 낙찰 시 PortOne V2 빌링키 기반 자동결제가 실행됩니다. 메인 API(POCAT) · 프론트엔드(pocat-front) · 채팅·알림 서버(pocat-worker) · 배치 서버(pocat-batch) · 모니터링 플랫폼(ai-monitoring), 5개 레포로 구성된 멀티 서비스 구조로 6주간 팀 프로젝트를 완료했습니다. 경매 입찰 동시성(Redisson tryLock), 결제 실패 복구(Redis Shadow Key), Outbox Relay 배치, n8n 기반 AI 로그 트리아지로 거래 안전성과 운영 관측성을 함께 구현했습니다. 전체 1,047+ commits, 29개 ADR로 모든 기술 의사결정을 문서화했습니다.

시스템 아키텍처 — 5개 레포 멀티 서비스

핵심 기술 문제 · 해결

1. Redis Redisson tryLock — 경매 입찰 동시성 제어

문제: 동시에 여러 사용자가 같은 경매에 입찰할 때 중복 낙찰이 발생할 수 있고, DB 유니크 제약만으로는 레이스 컨디션을 완전히 차단하기 어렵습니다.

기술 선택: Redisson tryLock(waitTime=0)으로 경매 ID를 키로 한 분산락 적용. waitTime=0이므로 락 획득 실패 시 즉시 실패 반환해 무한 대기 없이 동시 입찰 중 정확히 1건만 성공.

결과: k6 30 VU 동시 입찰 테스트 — concurrent_bid_successes = 1. 결제 동시성 30 VU — Rate Limit(429) 20건 + 결제 생성 성공 10건, confirmPayment에서 비관적 락으로 중복 차단.

2. Kafka 이벤트 드리븐 + 트랜잭션 커밋 후 발행 순서 보장

문제: 경매 입찰·낙찰·결제 처리 시 서비스 간 강한 결합으로 장애 전파. 또한 DB 트랜잭션 커밋 전 이벤트 발행 시 데이터 불일치 위험.

기술 선택: 경매 상태 변경을 Kafka 이벤트로 발행해 서비스 간 느슨한 결합 구현. 트랜잭션 커밋 후 이벤트 발행을 보장하기 위해 Spring의 TransactionSynchronization을 활용, afterCommit 훅에서 Kafka 발행 처리.

결과: 서비스 간 결합도 감소. DB 커밋 전 이벤트 발행으로 인한 데이터 불일치 문제 제거. 입찰→낙찰→알림 이벤트 체인의 순서 보장. 트레이드오프: afterCommit 훅 방식은 프로세스 크래시 시 이벤트 유실 가능성(Transactional Outbox 대비 내구성 낮음). 이 한계는 이후 6번 챕터의 Outbox Relay 배치로 보완했습니다.

3. Resilience4j Circuit Breaker — Gemini API 장애 격리

문제: Spring AI(Gemini) 카드 가격 추정 API가 외부 의존성으로, 장애 발생 시 연쇄적으로 경매 생성 기능 전체가 중단될 위험.

기술 선택: Resilience4j Circuit Breaker를 Gemini API 호출부에 적용. 장애 임계치(50% 실패 시 서킷 오픈) 설정, fallback으로 "가격 추정 불가" 기본값 반환해 경매 생성은 정상 진행.

결과: Gemini API 장애가 경매 생성 서비스로 전파되지 않아 핵심 기능 가용성 유지. 서킷 상태(오픈·클로즈드·반오픈)에 따른 자동 복구 동작 검증.

4. Redis TTL + 백업 스케줄러 이중화 — 경매 라이프사이클 관리

문제: 경매 종료 시점을 정확하게 처리해야 하나, Redis TTL 만료 알림만으로는 메시지 손실 위험. 단일 스케줄러는 서버 재시작 시 누락 가능.

기술 선택: Redis TTL + Keyspace Notification으로 경매 만료 1차 감지. 백업 스케줄러(auctionExpirationJob)를 pocat-batch에 ShedLock으로 이중화해 Redis 이벤트 손실 시에도 DB 상태 조회로 만료된 경매를 추가 처리.

결과: 경매 라이프사이클(생성→진행→종료→낙찰) 이중화로 단일 장애점 제거. 운영 중 Redis Cluster sub-second TTL 잘림 버그를 발견해 keyspace 전체 만료 이벤트 감지 방식으로 수정.

5. PortOne V2 빌링키 + Redis Shadow Key — 결제 실패 복구

문제: 낙찰 후 빌링키 자동결제가 실패했을 때 거래가 누락되면 판매자·구매자 모두 피해. 실패 탐지 타이밍과 재결제 허용 구간 관리가 필요.

기술 선택: 결제 실패 시 Redis Shadow Key를 설정(TTL=1시간). Shadow Key의 TTL 만료 이벤트(Keyspace Notification)를 감지해 '직접결제 가능 구간 종료'를 알림. 1시간 내 구매자가 직접결제하지 않으면 거래 취소 처리.

결과: 자동결제 실패 시에도 거래 누락 없이 복구 플로우 보장. 비관적 락으로 동시 결제 중복 차단. 운영 중 2등 낙찰자 직접결제 처리 버그를 발견해 수정.

6. Outbox Relay 배치화 — K-Com에서 얻은 교훈을 팀 프로젝트에 적용

문제: 메인 API 서버 안에서 Outbox Polling Publisher가 함께 실행되면 API 트래픽과 배치 부하가 같은 프로세스 자원을 경쟁하게 됩니다. 2번 챕터의 afterCommit 방식은 단순하지만 프로세스 크래시 시 이벤트 유실 위험이 남아있었습니다.

기술 선택: Outbox Relay → Reaper → Cleanup 3단계 Step으로 구성된 Spring Batch Job을 pocat-batch 레포로 완전히 분리. Relay Step이 미발행 레코드를 Kafka로 발행하고, 실패 시 Reaper Step이 재시도 대상으로 회수, Cleanup Step이 처리 완료 레코드를 정리합니다.

결과: API 서버와 배치 서버의 자원 경쟁 제거. 개인 프로젝트 K-Com에서 단일 서버로 탐구했던 Transactional Outbox 패턴을 멀티 인스턴스 배치 서버 규모로 확장 적용한 경험.

7. n8n + Loki — 장애 로그 AI 자동 트리아지

문제: Prometheus 메트릭과 애플리케이션 로그가 분리되어 있어 장애 발생 시 원인 파악에 수동 로그 검색이 필요했습니다. 결제·경매·AI 등 서로 다른 담당 영역의 로그가 한 곳에 섞여 있어 알림 노이즈가 컸습니다.

기술 선택: Loki로 로그를 ERROR/WARN/INFO 레벨과 태그([PAYMENT_ESCALATION], [AUCTION_ANOMALY], [CARD_SYNC] 등)로 수집. Grafana Alert Rule이 LogQL 쿼리로 이상 패턴을 감지하면 n8n 워크플로우를 트리거하고, n8n이 관련 로그를 태그별로 그룹핑해 Gemini로 1차 원인 분석 후 태그별 Slack 채널로 전송.

결과: 장애 발생 시 담당자가 로그를 직접 뒤지기 전에 AI 분석 결과가 먼저 전달됩니다. 결제·경매·AI 영역별로 알림이 자동 라우팅되어 책임 소재 파악 시간이 단축됩니다.

설계 결정

왜 멀티 레포로 분리했는가 — 채팅·배치를 메인 API에서 분리

초기에는 단일 Spring Boot 애플리케이션에 경매·결제·채팅·스케줄러가 모두 포함되어 있었습니다. 채팅 WebSocket 연결이 늘어날수록 같은 프로세스의 경매·결제 API 응답 시간에 영향을 줄 위험이 있었고, @Scheduled 스케줄러는 인스턴스를 늘릴 때마다 중복 실행 문제가 생겼습니다. 채팅·알림을 pocat-worker, 스케줄링을 pocat-batch(ShedLock)로 분리해 각 영역이 독립적으로 장애 격리·스케일링되도록 했습니다. 완전한 MSA 전환보다는, 장애 영향 범위가 큰 영역부터 우선 분리하는 점진적 접근을 택했습니다.

왜 afterCommit 훅을 Outbox Relay 배치로 보완했는가

afterCommit 훅은 구현이 단순하지만 프로세스 크래시 시 이벤트 유실 가능성이 있습니다. 처음엔 경매 이벤트의 실시간성을 우선해 단순성을 선택했지만, 결제·정산처럼 유실이 치명적인 흐름에는 Transactional Outbox가 필요했습니다. K-Com 개인 프로젝트에서 먼저 탐구한 Outbox 패턴을 pocat-batch의 Relay·Reaper·Cleanup 3단계 배치로 재구현해, API 서버 부하와 분리된 형태로 팀 프로젝트에 적용했습니다.

왜 n8n으로 AI 로그 트리아지를 도입했는가

Grafana Alert만으로는 "무엇이 위험하다"는 신호만 오고 "왜 위험한지"는 담당자가 직접 로그를 검색해야 했습니다. n8n으로 Grafana 알림 → Loki 로그 재조회 → Gemini 분석 → Slack 전송을 자동화해, 1차 원인 분석을 사람보다 먼저 받을 수 있게 했습니다. 결제·경매·AI 영역별 태그로 그룹핑해 무관한 담당자에게 알림이 가지 않도록 했습니다. 완전한 자동 복구보다는 "사람의 의사결정을 더 빠르게" 만드는 데 목적을 두었습니다.

왜 Spring AI + Redis Vector Store인가 — Pinecone 대신

외부 벡터 DB(Pinecone 등) 도입 시 추가 과금·레이턴시·인프라 복잡성이 증가합니다. 이미 운용 중인 Redis 인프라로 Vector Store를 구성해 추가 비용 없이 RAG 파이프라인을 구현했습니다. 카드 시세 추정에 요구되는 검색 정확도 수준에서는 Redis Vector Store로 충분하며, 대규모 트래픽 전환 시점에 전용 벡터 DB로 마이그레이션할 수 있는 인터페이스를 유지했습니다.
