Overview

포켓몬 카드 수집가들을 위한 실시간 경매 및 거래 플랫폼입니다. 경매 생성·입찰·낙찰·결제 전 과정을 Kafka 이벤트 드리븐 아키텍처로 연결해 서비스 간 느슨한 결합을 구현했습니다. Spring AI(Gemini)를 활용한 카드 이미지 분석으로 시세를 자동 추정하고, Resilience4j Circuit Breaker로 외부 API 장애 격리를 적용 중입니다. 현재 활발히 개발 진행 중인 프로젝트로, 662+ commits와 14개 ADR이 누적되어 있습니다.

시스템 아키텍처

핵심 기술 문제 · 해결

1. Kafka 이벤트 드리븐 + 트랜잭션 커밋 후 발행 순서 보장

문제: 경매 입찰·낙찰·결제 처리 시 서비스 간 강한 결합으로 장애 전파. 또한 DB 트랜잭션 커밋 전 이벤트 발행 시 데이터 불일치 위험.

기술 선택: 경매 상태 변경을 Kafka 이벤트로 발행해 서비스 간 느슨한 결합 구현. 트랜잭션 커밋 후 이벤트 발행을 보장하기 위해 Spring의 TransactionSynchronization을 활용, afterCommit 훅에서 Kafka 발행 처리.

결과: 서비스 간 결합도 감소. DB 커밋 전 이벤트 발행으로 인한 데이터 불일치 문제 제거. 입찰→낙찰→알림 이벤트 체인의 순서 보장. 트레이드오프: afterCommit 훅 방식은 프로세스 크래시 시 이벤트 유실 가능성(Transactional Outbox 대비 내구성 낮음). 경매 이벤트 규모에서는 단순성을 우선했으며, 유실 방지가 중요한 결제/정산은 별도 보상 트랜잭션으로 처리.

2. Resilience4j Circuit Breaker — Gemini API 장애 격리

문제: Spring AI(Gemini) 카드 가격 추정 API가 외부 의존성으로, 장애 발생 시 연쇄적으로 경매 생성 기능 전체가 중단될 위험.

기술 선택: Resilience4j Circuit Breaker를 Gemini API 호출부에 적용. 장애 임계치(50% 실패 시 서킷 오픈) 설정, fallback으로 "가격 추정 불가" 기본값 반환해 경매 생성은 정상 진행.

결과: Gemini API 장애가 경매 생성 서비스로 전파되지 않아 핵심 기능 가용성 유지. 서킷 상태(오픈·클로즈드·반오픈)에 따른 자동 복구 동작 검증.

3. Redis TTL + 백업 스케줄러 이중화 — 경매 라이프사이클 관리

문제: 경매 종료 시점을 정확하게 처리해야 하나, Redis TTL 만료 알림만으로는 메시지 손실 위험. 단일 스케줄러는 서버 재시작 시 누락 가능.

기술 선택: Redis TTL + Keyspace Notification으로 경매 만료 1차 감지. 백업 스케줄러(ShedLock)를 이중화해 Redis 이벤트 손실 시에도 DB 상태 조회로 만료된 경매를 추가 처리.

결과: 경매 라이프사이클(생성→진행→종료→낙찰) 이중화로 단일 장애점 제거. 서버 재시작 후에도 누락된 경매 종료 처리 보장.

설계 결정

왜 afterCommit 훅인가 — Transactional Outbox 대신

Transactional Outbox 패턴은 내구성이 높지만 Outbox 테이블 관리·Polling Publisher 구현 복잡성이 추가됩니다. 경매 이벤트는 실시간성이 우선이고 낙찰·알림 유실 시 재시도 허용 설계(보상 로직 존재)로 단순성을 선택했습니다. 결제·정산처럼 절대 유실 불가 도메인은 별도 보상 트랜잭션으로 처리합니다.

왜 Redis TTL + 백업 스케줄러 이중화인가

경매 종료 이벤트를 단일 스케줄러에만 의존하면 서버 재시작 시 누락 가능성이 있습니다. Redis TTL Keyspace Notification은 즉시 트리거되지만 Redis 장애 시 손실됩니다. 두 방식을 이중화해 어느 한쪽이 실패해도 DB 상태 조회로 복구할 수 있게 했습니다. 단, 이중화로 인한 중복 처리를 막기 위해 경매 종료 처리에 DB 수준 상태 체크를 추가했습니다.

왜 Spring AI + Redis Vector Store인가 — Pinecone 대신

외부 벡터 DB(Pinecone 등) 도입 시 추가 과금·레이턴시·인프라 복잡성이 증가합니다. 이미 운용 중인 Redis 인프라로 Vector Store를 구성해 추가 비용 없이 RAG 파이프라인을 구현했습니다. 카드 시세 추정에 요구되는 검색 정확도 수준에서는 Redis Vector Store로 충분하며, 대규모 트래픽 전환 시점에 전용 벡터 DB로 마이그레이션할 수 있는 인터페이스를 유지했습니다.
