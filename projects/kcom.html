Overview

스타벅스 사이렌 오더에서 모티브를 얻은 전국 프랜차이즈 스마트 오더 시스템입니다.
주문·재고·알림 처리를 Kafka (KRaft 모드) 이벤트로 연결한 이벤트 드리븐 분산 아키텍처를 탐구했습니다.

Transactional Outbox 패턴으로 주문과 이벤트 발행의 원자성을 보장하고,
Redis ZUNIONSTORE로 7일 슬라이딩 윈도우 인기 메뉴 집계를 구현해 응답속도를 +80% 향상시켰습니다.

Ready's7 팀 프로젝트에서 Redisson tryLock을 학습한 뒤,
Watchdog 자동 갱신과 Facade 계층 분리로 분산 락 패턴을 더 깊이 탐구하는 목적으로 진행한 개인 심화 프로젝트입니다.

Tech Stack

시스템 아키텍처

핵심 기술 문제 · 해결

1. Transactional Outbox + ShedLock — 주문과 Kafka 발행의 원자성 보장

문제: 주문 DB 저장과 Kafka 발행을 별도 트랜잭션으로 처리하면, DB는 커밋됐으나 Kafka 발행 실패 시 데이터 불일치 발생. Kafka 장애 시 주문 손실 가능성.

기술 선택: Transactional Outbox 패턴 적용 — 주문 저장과 Outbox 레코드 삽입을 단일 DB 트랜잭션으로 묶어 원자성 보장.
ShedLock 기반 Polling Publisher가 Outbox 테이블을 주기적으로 조회 → Kafka 발행 후 처리 완료 표시.

결과: Kafka 장애 시에도 Outbox 레코드 보존 → 서비스 복구 후 재발행 가능. 주문 손실 없는 At-least-once 발행 보장.
소비 측 처리: At-least-once는 중복 발행이 발생할 수 있으므로,
컨슈머는 outbox_id를 이벤트 키로 사용해 DB unique constraint로 멱등성 보장, 중복 소비 시 noop 처리.

2. Facade + Redisson Watchdog — 분산 락 조기 해제 방지

문제: 주문 처리 로직이 길어질 경우 Redis 락의 TTL이 만료되기 전 작업이 완료되지 않아 락이 조기 해제되는 문제(lock expiration before task completion). 다른 요청이 락을 취득해 중복 처리 발생 가능.

기술 선택: Redisson Watchdog 메커니즘 활용 — 락 보유 중 자동으로 TTL 갱신(기본 30초 주기)해 작업 완료 전 락 만료 방지.
Facade 레이어에서 락 획득·해제를 캡슐화 → 서비스 코드의 분산 락 직접 의존 제거.

결과: 장시간 처리 작업에서도 락 조기 해제 없이 안전하게 임계 구역 보호. Facade 패턴으로 락 로직 중복 제거 및 테스트 용이성 향상.

3. Redis ZUNIONSTORE — 7일 슬라이딩 윈도우 인기 메뉴 집계

문제: 인기 메뉴 집계를 매 요청마다 DB에서 GROUP BY·ORDER BY로 처리하면 높은 쿼리 비용. 실시간성과 성능 사이의 트레이드오프 필요.

기술 선택: 매일 주문 데이터를 Redis Sorted Set(날짜별 키)에 기록.
조회 시 ZUNIONSTORE로 7일치 Sorted Set을 합산해 인기 메뉴 랭킹 산출.
스케줄러로 오래된 날짜 키 자동 삭제 → 7일 슬라이딩 윈도우 유지.

결과: DB GROUP BY 집계 쿼리(로컬 MySQL, 주문 데이터 1,000건 기준 약 120ms) 대비 Redis ZUNIONSTORE 조회(약 24ms)로 응답속도 +80% 향상. 슬라이딩 윈도우 방식으로 최신 7일 데이터 기반 정확한 인기 메뉴 제공.

성과

+80% Redis offloading으로 인기 메뉴 응답속도 향상

설계 결정

왜 Transactional Outbox인가

단순 try-catch로 Kafka 발행 실패를 처리하면 DB는 커밋됐으나 이벤트가 손실되는 "부분 실패"를 해결할 수 없습니다. 2PC(Two-Phase Commit)는 DB와 Kafka 간 분산 트랜잭션이 불가하고, Saga 패턴은 보상 트랜잭션 복잡성이 높습니다. Outbox 패턴은 단일 DB 트랜잭션만으로 원자성을 보장하며 구현 복잡성이 가장 낮습니다.

왜 KRaft 모드 Kafka인가

ZooKeeper 의존성을 제거해 로컬 개발 환경을 경량화하기 위한 선택입니다. Kafka 3.x 이후 KRaft가 프로덕션 준비(GA) 상태이며, ZooKeeper 별도 실행 없이 Docker Compose 설정이 단순해집니다. 개인 프로젝트에서 최신 Kafka 아키텍처를 직접 탐구하는 목적도 있었습니다.

왜 ShedLock을 Outbox Publisher에 사용했는가

Outbox Polling Publisher를 다중 인스턴스로 수평 확장하면 같은 Outbox 레코드를 여러 인스턴스가 동시에 발행하는 중복 발행 문제가 발생합니다. ShedLock은 DB 락 기반으로 특정 시점에 하나의 인스턴스만 스케줄 작업을 실행하게 보장해 At-least-once를 정확히 구현할 수 있습니다.
